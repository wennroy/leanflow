# 本地安装后的 leanflow 验收 Prompt

以下内容可直接交给一个新 agent。测试结果由实际执行产生，本文不是测试通过报告。

---

请在当前 harness 中验收我已经通过本地安装方式装好的 leanflow 插件，预期版本 0.3.2。
你的任务是使用已安装插件执行真实工作流并报告问题，不是继续开发 leanflow。

报告路径固定为 `~/leanflow-acceptance/<harness>/<run-id>/acceptance-report.md`。
`<harness>` 用当前宿主名称的简短标识，`<run-id>` 用开始时间 `YYYYMMDD-HHMMSS`；
将 `~` 展开为实际用户目录。先报告完整绝对路径；不同运行不覆盖。我会把这份 Markdown
交回负责 leanflow 开发的 agent，由它根据证据裁决缺陷与后续修改。

## 测试范围与边界

1. 先确认当前宿主能发现哪些 leanflow 入口，记录插件版本、实际安装来源和调用方式。
   原生 slash command 或宿主迁移后的等价 skill 都可以，但要写清实际使用的是哪一种。
   如果插件尚未加载、版本不对或工具缺失，先报告具体问题；不要改用源码目录模拟安装成功。
2. 在本次报告目录下的 `fixtures/` 建立独立 Git 测试项目，证据放 `evidence/`，结束后保留
   以便复核。不要修改原 leanflow 仓库、已安装插件或其他
   业务项目，不 push、部署、创建 PR、改全局配置。测试项目的本地提交与 worktree 操作允许。
3. 必要时安装最小项目测试依赖；不要引入登录、付费服务、真实账号或生产数据。
4. 每个案例实际调用插件入口，记录动作与产物。不能只读指令推断通过，也不能自己补上
   插件漏掉的流程后报告通过。发现问题保留复现证据，继续无依赖案例，不修改被测插件。
5. 不为了验收而把所有任务升级为 max，也不为了用完预算反复派 Agent。执行阶段使用已安装
   插件的方法；验收阶段对照下面的标准。不要把测试脚本伪造的 Review 输出当成真实审查。
6. 同一连续会话只能证明同会话续跑。跨会话恢复需要干净的新上下文；若无法自己建立，
   最后给我一段含测试项目路径和任务 id 的续测 Prompt，明确标为「待新会话验证」。

## 测试项目

建立一个足够小、无需后端的浏览器待办列表：增加事项、标记完成、筛选和本地持久化。
用普通 HTML/CSS/JavaScript 和本地服务器即可；准备可复跑的基础检查。
保留一个稳定起始提交，不同案例使用独立测试仓库副本或隔离分支，避免前一案例影响下一案例。
只有专门测试跨 worktree 恢复时才共享任务记忆。

## 按顺序执行

### A. low 直接开发

请求：`/leanflow:execute --level low 让新增待办忽略纯空白输入，并清理文本首尾空白。先不提交代码，给我 UAT 步骤。`

观察：无现成 plan 也能直接实施；没有 Review Agent、其他子 Agent 或 Playwright；有相关
低成本检查和具体 UAT；每个需求一份本地记录，没有为子任务创建 .sdd/plan/handoff。
记录开始时间、第一次有效产出时间、结束时间和记忆写入次数。不要代替我批准 UAT。

### B. 默认值、显式选档与 plan 边界

在独立案例中设置项目默认 low，再调用：
`/leanflow:plan --level HiGh 为待办列表增加“只看未完成”筛选。`

观察：大小写被归一化为 high；只生成方案、不改产品代码；项目默认仍是 low。
使用任务 id 调用 execute，不再次指定 level，观察是否继承 high。
本案例同时作为 high 测试：应实际运行关键旅程 Playwright，保留可复跑测试，Review ≤3 次。
若测试工具不可用，标记环境阻塞，而非降成 low 或声称 E2E 通过。

### C. medium 与审查预算

在独立案例中请求 medium 修复一个预先可复现的状态 bug，例如删除事项后“未完成数量”未更新。
让插件实际实施和审查。检查范围内明确 bug 是否自主修复，reviewer 调用（含修后复核）≤2，
没有专门 Playwright，必要的产品取舍才询问用户。

若实际首审无 finding，一次结束是正确行为，不强造第二轮。核对低成本检查是否覆盖原 bug；
未覆盖就明确留 UAT，不能用无关绿灯代证。medium 默认不启动浏览器，脚本放在 tests/ 也不例外。
额外用独立的工具契约测试核对
预算耗尽会拒绝下一次预留，明确区分“工具预算测试”与“真实 Agent 行为”。不要篡改正式案例
计数来伪装已运行审查。

### D. 改档与 xhigh

在一个已有有效验证记录的案例中明确改为 xhigh，补测约定的异常/边界场景。
观察：只补新增或失效检查，累计次数保留；不得删除断言、skip 失败用例来声称通过。
实际修改产品代码后，必需的定向 Review 不能自行省略；检查任务 checks/delivery 是否与证据一致。
再明确改为 low，检查是否保留已有问题与 UAT，而不是把它们改成通过。
如果没有自然出现无进展循环，该项标「未覆盖」；可单独验证工具的连续两轮无进展限制，
但不要用模拟结果替代 Agent 层面的真实循环测试。

### E. max 完整小需求

在独立项目中请求：
`/leanflow:execute --level max 做一个本地待办列表，支持新增、完成状态、全部/未完成筛选和刷新后保留数据。不要加账号、同步、通知或其他产品方向。`

观察：有产品场景补全，适合独立开发的工作通过 implementer 执行，完成集成、测试、审查与修复。
不会为每个微小步骤派 Agent 或生成记忆文件；不自行增加产品方向，不承诺后台持续运行。
Review 默认 ≤8，总 Agent 调用默认 ≤24；它们是上限，不是需要达到的次数。
无法完成时真实留下阻塞/缺口，而不是强行标 done；自动验证不等于我已通过 UAT。

### F. Memory、恢复与导出

选一个已实施、awaiting_uat 的任务：

- 检查记忆位于 Git common dir 的 leanflow/tasks，下属每个需求只有一份 Markdown；Git 索引
  没有任务记忆。项目记忆可选，原始 Playwright 产物不算额外任务记忆。
- 在新 worktree 查看该任务：应能找到共享记录，但必须核对代码；原 worktree 独有的未提交
  实现不能被当成新 worktree 已有代码，不能无理由重做实现。
- 准备一次干净新会话续跑。新会话应恢复目标、决定、待 UAT 与预算，不能重复实施/重审。
- 只有我实际反馈「UAT 通过」后才完成该项。你可以列出手工步骤供我操作；不要自行制造
  我的确认。没有得到确认就以 awaiting_uat 结束，这是正确行为。
- 在单独明确的导出请求下执行 memory export。docs 中应出现精选快照；原记录保留，
  不覆盖已有同名文档，不自动 git add/commit。导出请求不代表 UAT 已通过。
- 在另一个非 Git 目录创建有默认档位、已消耗预算的任务，再初始化 Git 并执行 memory
  migrate。任务正文、默认档位和累计次数应保持；后续按原 id 恢复，Git 不追踪记忆。
  若单独使用状态工具验证该项，标为工具契约测试，不能算作已验证 Agent 行为。

## 输出一份验收结果

只维护开头指定的一份 `acceptance-report.md`，按案例完成时更新，避免中断丢失已有证据；
不为每个案例另写报告。终答给出绝对路径和简短结论。即使插件未加载或整个测试阻塞，
也应写出这份报告，列清已尝试的发现方式及错误。

- 环境：harness 名称与版本、系统、插件来源/版本及文件内容摘要或校验值、实际入口、
  模型与模型 effort（能获取才记录），与 leanflow level 分开；测试项目与起始提交。
- 案例表：实际请求、实际入口、通过/失败/阻塞/未覆盖、证据位置。
  “通过”必须有真实动作与结果；缺证据写未覆盖。每项引用本报告目录内的相对证据路径，
  附关键命令、退出码、必要的原始输出或会话事件片段，不只写“按预期完成”。
- 成本表：每个案例耗时、Agent/Review 次数、记忆文件和写入次数、重复询问/重验次数。
  写明数据如何采集；拿不到的指标标不可用，不估计。token 不要用账号级用量代替。
  从 new 起累计任务写入为 revision+1，包含 level/reserve/budget；default 和导出单列。
  耗时区分模型工作、工具运行、宿主等待/中断与采集延迟；记录同时加载的其他技能。
- 问题清单：稳定编号 LF-001 等、建议严重程度、受影响案例、最短复现步骤、预期与实际
  差异、关联证据、复现是否稳定。分类为疑似插件缺陷、harness 限制、环境问题或尚不确定；
  不要在缺证据时强行归因。保存有关的任务 Markdown 快照和 Git diff，隐藏凭据。
- 已跑和未跑的范围，以及仍需我亲自执行的 UAT 或新会话恢复步骤。
- 待裁决项：集中列出需要开发 agent 进一步确认的问题，不修改插件，也不把“暂无发现”
  写成“所有场景已通过”。

不要依据单次测试声称提速百分比。不要将说明文档中的预期行为当成实测证据。
遇到缺陷继续完成不依赖它的测试，最后集中汇报；涉及我必须做的安装、产品决定或 UAT 时才暂停对应项。
