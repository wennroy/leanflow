# /leanflow:plan

把 `$ARGUMENTS` 变成一份落盘的、可执行的 plan。

## 0 · 输入

- `$ARGUMENTS` 为空 → 只问一句：「要做什么？」然后继续。
- 用户贴了现成需求文档 / issue → 直接当需求用，不复述、不确认。

## 1 · 澄清（决策树 + 分轮批量；禁止审讯，也禁止猜）

目标：**落笔前没有任何悬而未决的假设**。

把需求的不确定性建模成决策树：每个决定分出依附于它的子决定。
分轮处理，每轮问整个"边界层"（= 前置已确定、现在可问的所有决定）：

- **明确**：目标、范围、约束能从描述或代码推断 → 直接进 2。
- **有未知** → 按轮澄清：
  1. 用一次 AskUserQuestion 把整个边界层问完（工具上限 4 题/轮，
     超出按依赖顺序排到后面的轮次）。
  2. **每题必须附推荐答案**——用户可以回「都按推荐」一键过完一轮。
  3. 用户回答后重算边界层：已定决定解锁子决定，问下一轮。
     依赖本轮未决项的问题不许猜，留给后面的轮次。
  4. **事实自己查**：问题涉及的代码现状（现有实现、约束、历史），
     读文件或派 Explore subagent 查——永不问用户"系统现在是什么样的"。
     只有"决定"才问用户。
- 终止条件：边界层为空。此时才进 2。

禁止：一次一个问题（按轮不按题）；把能查到的事实当问题问；
不问就动手猜。

## 2 · 勘察（时间盒，不务虚）

目的只有一个：确定**每个任务改哪些文件、verify 命令怎么写**。

- 先读 CLAUDE.md 和需求直接相关的文件；第 1 步查过的事实直接复用。
- 需要跨模块广泛摸底 → 派 1 个 Explore subagent（本命令唯一允许的
  subagent），一次把问题问全。
- 勘察到能写出 plan 就停，不写调研报告。

## 3 · 落盘 plans/<kebab-case-名>.md

plan 是写给**零上下文的执行者**的（可能是 /compact 后的自己，可能是
implementer subagent）：每个任务脱离本会话也能看懂、能独立验收。

严格按此模板：

    # <功能名>
    > 状态：进行中

    ## 目标
    <≤3 句：做完后世界有什么不同>

    ## 非目标
    <本次明确不做的，防 scope 蔓延>

    ## 关键决定
    <澄清阶段定案的决定，一行一条：问题 → 结论。review 阶段按此验收>

    ## 假设
    <仅剩用户明确说"你定"的默认项。理想状态是空的>

    ## 全局验收
    `<命令，如 pnpm typecheck && pnpm test>`

    ## Tasks
    - [ ] T1 <标题> [顺序]
      - 改动：`src/a.ts`（改）、`src/b.test.ts`（新）
      - 要点：<2-3 句：关键决策、坑、接口约定。不教基础知识>
      - verify: `<可原样执行的命令>`
    - [ ] T2 <标题> [独立]
      ...

模板规则：

- **4–8 个任务**，每个 30min–2h 量级。超过 8 个说明该拆 plan，
  少于 4 个考虑合并。
- **[独立]** = 与其他未完成任务没有共同文件，可并行/打包；
  **[顺序]** = 有依赖必须先来后到。标错 = 执行期冲突，宁可标保守。
- **verify** 必须原样可跑（如 `pnpm test -- src/foo`），
  禁止「运行相关测试」这种描述；没有自动化验证手段的任务，
  写清人工验收点并标 `[人工]`。
- 全局验收 = 全部任务完成后的终验（typecheck + test + lint
  或项目等价物）。

若目标 plan 文件已存在：先读出现有内容，告诉用户差异，
问「更新还是另建」。

## 4 · 收尾（一句话）

「plan 已落盘 plans/xxx.md。直接改，或 /leanflow:execute plans/xxx.md 开跑。」
