# /leanflow:execute

执行 `$ARGUMENTS` 指定的 plan。

## 0 · 定位 plan

- `$ARGUMENTS` 为空 → 在 plans/ 里找「状态：进行中」的 plan：
  只有一个就用它；多个列出让用户选；一个没有就提示先 /leanflow:plan。
- 读 plan 全文。「关键决定」「假设」两节是全程约束，执行不得违背。

## 1 · 建任务列表

- 用 TaskCreate 把**未勾选**任务建成任务列表（已勾选 = 已完成，跳过
  ——这就是断点续跑，/compact 或新会话后重跑本命令即可继续）。
- 全部已勾选 → 直接进第 4 步。

## 2 · 主循环（按 plan 顺序处理）

每步先向下扫描：从当前任务起**连续 ≥2 个 [独立] → 打包派发**；
否则**内联执行**。

### 内联执行

1. 按「要点」实施，只碰「改动」里列的文件。
2. 跑该任务的 verify 命令：
   - 过 → 勾选（立即 Edit plan 的 checkbox）→ 提交（见第 3 步）→
     一行回报。
   - 败 → 内联修；同一任务修 3 次仍败 → 停下，把命令输出给用户，
     等指示。

### 打包派发（连续 ≥2 个 [独立]）

用 Agent 工具派**一个** leanflow:implementer 承接整包，prompt 只含：

- 这几个任务的段落原文（标题、改动、要点、verify）
- plan 的「关键决定」「假设」节
- 回报格式：每任务 diff 摘要（≤5 行）+ verify 输出；禁止长叙述

implementer 顺序完成包内任务、逐个跑 verify。回报后：

- 全过 → 逐个勾选、逐个提交、一行汇报。
- 有失败 → 失败任务拆回内联，按内联规则处理。

禁止：把整份 plan 或会话历史塞给 implementer；
**一个任务一派**（那是 superpowers 的做法，不是我们的）。

### [人工] 任务

执行到位后停下，请用户按 plan 中的验收点确认，确认后才勾选。

### plan 错了怎么办

执行中发现要点与实际不符、漏任务、顺序有误：
**先 Edit plan 修正，再继续**。plan 是活文档，不硬撑。

## 3 · 提交规则

- 只有主会话能 git commit；implementer 永远不提交。
- 每个任务 verify 通过后提交一次；message 先看 git log 学项目风格，
  缺省用 `T<n> <任务标题>`。
- 工作区存在 plan 之外的未提交改动 → 先问用户怎么处理。

## 4 · 全局验收

全部勾选后跑 plan 的「全局验收」命令：

- 过 → 「plan 执行完毕，下一步 /leanflow:review。」
- 败 → 当新任务内联修，3 次仍败停下给用户看。

## 全程规则

- 进度回报每任务一行，不写小作文。
- dispatch 预算：典型 0–2 次（= 连续独立段数），绝不逐任务派发。
- 用户随时可打断；打断后重跑本命令从 checkbox 续跑。
