# /leanflow:execute

执行 `$ARGUMENTS` 指定的 plan，覆盖从实现到验收归档的日常流程。
先读取 `${CLAUDE_PLUGIN_ROOT}/references/completion.md`，按其中的证据、
暂停和归档规则执行。不要求用户另行输入 review、verify、finish 才能收尾。

## 0 · 定位与恢复

- 参数为空 → 在 `plans/` 找未完成 plan，包括进行中、待裁决、待验收和阻塞；
  只有一个就用它，多个让用户选，没有则提示先 plan。已归档 plan 不自动重开。
- 读 plan 全文，目标、非目标、关键决定和假设都是约束。
- 按共用规则建立或核对执行记录、基线和工作区改动。已有验证、复审和用户
  裁决仍有效时直接复用；从尚未完成的阶段继续。
- 用 TaskCreate 跟踪未验收任务，plan 是持久化依据。全部任务已勾选也要检查
  复审与收尾状态；已经实施但等待人工确认的任务不重复实施。

## 1 · 实施与任务验证

保持内联优先：按 plan 顺序扫描，连续 ≥2 个可由 agent 自动验收的
`[独立]` 任务打包给一个 implementer，其余内联执行。

### 内联执行

1. 按任务要点实施，默认只碰列出的文件。
2. 跑任务 verify，记录它证明的验收结果；失败时读取
   `${CLAUDE_PLUGIN_ROOT}/commands/debug.md` 的调试方法，在当前流程内定位修复。
   同一任务连续 3 次修复仍失败，记录证据与阻塞原因，停止盲目重试。
3. 自动验收通过后记录证据、勾选、按提交规则提交，一行汇报。
   提交失败也要记录，续跑处理未完成的提交，不重新实现已验收代码。
4. `[人工]` 项实施完成后记录「已实施，待人工验收」，暂不勾选，集中收集
   验收点；继续无依赖的任务。依赖人工结果才能继续的任务须等待。

### 打包派发

用 Agent 工具派一个 leanflow:implementer 承接整包，prompt 包含：

- 任务原文：标题、文件、要点、验收结果、verify 命令。
- 与任务有关的目标、非目标、关键决定、假设和依赖。
- 每任务 diff 摘要、验证证据和偏差的简短回报要求。

不派发等待用户输入或人工验收的任务，不把整个会话历史塞给 implementer，
不逐任务派发。implementer 在共享工作区顺序执行；主会话不同时改同一批文件。

回报后核对改动与证据，逐个记录、勾选和提交；失败项回到内联调试，保留
已经尝试过的证据。分提交时仅暂存对应任务改动，不能把整包或用户已有改动
一并提交；不能可靠拆分时说明并按实际依赖调整提交边界。

### 计划调整与提交

- 实施细节、必要文件或顺序与实际不符时，先修订 plan 再继续；修改目标、
  关键决定、验收标准或扩大范围时须由用户决定，不能为了过关降低验收标准。
- 只有主会话能 commit；每个任务验收通过后提交一次，先看 git log 学风格，
  缺省用 `T<n> <任务标题>`。用户另有提交要求时遵从。
- 用户已有改动保留原样，仅在确实冲突或无法分离时询问。

## 2 · 验证与独立复审

- 自动任务均已验收、人工任务已实施后，执行共用规则的「验证」。
- 自动验证通过后读取 `${CLAUDE_PLUGIN_ROOT}/commands/review.md`，在当前流程内
  派一次独立 reviewer 审全量改动；不要求用户手动调用 review。
- 无问题 → 继续收尾。有问题 → 集中呈现、记录待裁决状态；按用户裁决修复、
  定向验证和复核。已有有效复审与裁决的续跑不重新派完整复审。
- 内部 review 完成后返回本流程，不让两个命令相互递归调用。

## 3 · 人工验收与归档

- 汇总仍未确认的人工验收项，等待用户明确结果；不能把自动验证或用户沉默
  当成人工验收通过。用户报告问题时回到实施和受影响的验证、复审。
- 用户确认通过的项目逐项记录、勾选，并按既定提交规则处理尚未提交的改动。
  只确认一部分时，其余项目继续保持待验收，不能整批默认通过。
- 按共用规则检查归档条件。齐备即自动归档；不齐备则记录待办和当前阶段，
  下次 execute 或用户提供所需输入后从该阶段继续。
- 收尾报告包含验证、复审处置、归档位置和 Git 状态，保持简短。

进度每任务一行，通常只需 0–2 次 implementer 派发，加一次独立 reviewer。
用户随时可以打断或要求只做到指定阶段。
