# /leanflow:review

可独立审查用户手写的改动，也可由 execute / finish 在收尾时调用。
读取 `${CLAUDE_PLUGIN_ROOT}/references/completion.md` 的验证和复审规则。
独立调用完成后报告结果；内部调用返回调用方，归档由调用方负责。

## 0 · 定范围

- 参数是 plan 路径 → 读 plan；参数是提交/分支/diff 范围 → 按该范围审。
- 无参数 → 优先使用会话已明确的 plan 或范围。没有 plan 时检查当前工作区
  改动；没有工作区改动且范围仍不明，或存在多个候选 plan 时，再问用户。
  不要求为了 review 新建 plan。
- 有 plan 时优先使用执行记录的基线；旧 plan 缺基线，先用可确定的分支或
  提交信息找起点，无法确定才询问。纳入本次范围内暂存、未暂存和未跟踪文件，
  排除用户已有的无关改动；不能只看 git diff 的默认输出。
- 对照 plan 与需求来源。无 plan 时使用用户要求、相关文档和项目约定；
  产品行为依据不足时说明未能验证的部分，不虚构需求。
- 续跑先读取已有结论和裁决，只处理待办与失效部分。用户明确要求重新全量
  复审时再重做，不能因重新进入命令自动重复完整复审。

## 1 · 独立复审

用 Agent 工具派一个 leanflow:reviewer，prompt 含：

- 范围、基线、工作区改动归属与必要的需求来源。
- 有 plan 时：目标、非目标、关键决定、假设、验收结果和已有验证证据；
  无 plan 时明确说明，用实际需求与 diff 复审。
- 输出格式要求，见 `${CLAUDE_PLUGIN_ROOT}/agents/reviewer.md`。

一次审全量改动，合并需求符合性与代码质量。reviewer 只读，不改代码或提交。
如果当前环境无法派发 agent，明确说明独立复审尚未完成；仅在用户接受替代
方式时由主会话复审并记录，不能冒充独立复审或据此直接归档。

## 2 · 集中裁决与修复

1. findings 原样呈现，不擅自过滤；集中请用户裁决：修 / 延期 / 不修。
   没有发现问题时直接报告，不增加确认步骤。
2. 有 plan 时记录结论、代码状态、裁决及待办；无 plan 时保留在当前会话，
   不创建计划文件。阻塞项延期或不修时，明确记录其影响与用户是否接受。
3. 按已有裁决修复；方案需要改变范围或产品取舍时再问。修复后按共用规则
   验证受影响部分，复用 reviewer 检查原问题是否解决；必要时才扩大复审。
4. 汇报已解决、已接受的遗留项、待裁决项与验证限制。内部调用返回调用方；
   独立调用到此结束，不再要求执行 verify / finish。

禁止未经裁决就批量修改复审 findings，或顺手实施范围外的建议。
