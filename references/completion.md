# 验证、暂停与收尾

本规则供 execute/review/verify/finish 共享。同一会话已经加载则复用。
完成的是验收结果，不是调用完某个命令；不重复索取已有授权。

## 验证

1. 对照用户目标、来源、决定、验收项核对实现，不能只按计划自证。
2. 按任务 level 跑相关检查；low 不引入重型测试框架或运行 Playwright，给出 UAT 步骤。
   medium 默认采用无需浏览器的相关单测/DOM/集成；high 以上执行约定的独立旅程验证。
   修 bug 时说明检查是否真的覆盖原触发路径；做不到低成本自动覆盖则留明确 UAT，不能用
   无关测试全绿证明故障已修。用户指定的浏览器检查按 levels 的覆盖规则处理。
3. 验证证据绑定范围、命令、相关代码/依赖/环境。证据有效则复用；变化或不确定时
   只补受影响检查。仅补进度、用户确认 UAT、整理本地记录，不重跑业务测试。
4. 检查实际 diff：暂存、未暂存、未跟踪内容都纳入；保留用户已有改动，排除无关项。
5. 如实区分通过、失败、未验证、不适用、待人工确认。测试退出 0、Stop hook 静默、
   reviewer 无发现，都不能代替没有被检查的验收项。

## Review 与修复

- low 跳过 Review，记「按 low 未复审」；其余档位遵循任务的累计预算。
- 有证据且符合既定目标的 bug 自动修复；可逆的实现细节自主处理并记录重要决定。
  产品取舍、范围扩张、放弃必需验收项集中交给用户。不要机械接受错误建议。
- 每条 finding 有稳定 id、证据/位置、有效性判断、处置（修复/不成立/延期/待决定）、复核状态。
  不成立需理由，延期需记录影响；仍影响必需验收的遗留项不能当作完成。
- “已修复”绑定当前交付的 worktree/代码状态和核对结果；别的分支修复不代表这里已包含。
  “已接受遗留/豁免”引用实际用户决定及其范围，待决定不能写成已接受。
- 修后定向验证并由 reviewer 复核原问题及受影响部分；每次请求复核都计入预算。
  没有新变化不重新全量审查，不让 review/execute 相互递归。

## 阶段与暂停

任务阶段：plan → implement → verify/review → awaiting_uat → done；另有
awaiting_decision、blocked。正文逐项区分已实施、自动验证完成、UAT 已通过。

- 未确认的人工项不阻止无依赖工作，最终集中验收；用户沉默或模型代替用户操作不算 UAT。
- 真实工具/环境缺失、预算不够完成必需审查、循环无进展：记录具体缺口、尝试和下一步，
  必要时 blocked；不能靠重建任务、换档或把阶段写成 done 来绕过。
- 暂停后先核对已有任务和代码，从缺口继续，已有决定和累计次数持续有效。
  派发中断先按原 Agent/请求标识查回结果，再判断是否需要新派发；没有结果就保留 pending，
  不从 reserve 次数推断审查完成，不自动退款或扩额。必要标识合入原任务，不另建调用日志。
- 已有改动的旧任务缺少基线时，回溯实施前提交；无法确定就保留缺口并询问。
  只有完全未实施的新任务才能用当前 HEAD 作为起点。

## 交付与归档

进入 awaiting_uat 或 done 前，在同一次 `LF checkpoint --revision N --phase ... --checks '<JSON>'`
中保存四项交付摘要，仍在原任务 frontmatter，不增加文件或额外写回。JSON 结构为：

```json
{
  "verification": {"status": "passed", "evidence": "正文验证节：相关范围、代码指纹、命令与结果"},
  "review": {"status": "not_applicable", "evidence": "low 档跳过，未做独立审查"},
  "e2e": {"status": "not_applicable", "evidence": "low 档跳过，未运行浏览器"},
  "uat": {"status": "pending", "evidence": "等待用户按正文 UAT 步骤验收"}
}
```

示例是 low；按真实档位/结果填写。状态只用 passed/pending/failed/not_applicable/waived：
- verification 对应所选档位要求的相关自动检查；未覆盖的人工路径仍明确列在 UAT 中。
- review：medium 以上必须有有效独立结论，修后待复核仍 pending；high 以上 e2e 必须有
  独立 tester 的旅程证据，非浏览器用 API/CLI 旅程，不能把整个 e2e 标不适用。
- waived 仅用于用户明确免除某项要求，evidence 写决定来源/范围；不是“通过”。
  uat 的 passed 必须引用实际用户确认；用户免除 UAT 则用 waived，不能用 not_applicable。
- 每项 evidence 非空，可引用正文或已有产物；不要把长日志复制进 frontmatter。

读取工具返回的 delivery：automatic_complete 表示记录的自动必需项已完成；ready_for_uat
表示可进入完整 UAT（可能含明确豁免）；ready_for_done 还要求人工项已确认且无阻塞。
允许保留 awaiting_uat 让用户先验独立部分，但 ready_for_uat=false 时必须同时报告缺口，
不能把该阶段名当作流程通过。没有 Review 派发、只有待处理结论、仍有失败，均不能宣称完整通过。
工具拒绝缺少四项摘要的交付 checkpoint，以及 ready_for_done=false 的 done；不会核验
证据真假或自动感知所有代码变化，协调者仍须检查指纹/环境及未解决的必需 finding。
代码/范围变化时把受影响摘要改为 pending；reserve reviewer/tester 会使对应旧结论待更新。
旧记录缺摘要时先复用并核对已有证据补齐，不因升级格式重跑检查。降档不自动清除历史缺口；
原 pending/failed 项需解决或记录用户豁免，不能改成不适用；保留实际失败历史与证据链接。

全部约定验收已满足、证据有效、所需复审完成、人工项已确认且无未接受的阻塞项，
才标 done。按 low 跳过或用户明确调整的要求记录为跳过，不能写「通过」。

新任务原地保留在本地 tasks/<id>.md，done 即逻辑归档；不移动/复制多份文件。
不自动写 docs。用户要归档文档时按 memory export 生成精选快照，再按提交授权处理。

代码按完整改动批次提交，只有主协调者操作 Git；先查看提交风格，只暂存本次改动。
用户要求暂不提交时遵从。push、PR、部署、merge、squash、删分支依据任务已有授权，
level 不扩大操作权限。提交失败记为待办，不重做已验证实现。

需要发布时按已授权目标准备构建/配置、迁移与回滚办法、发布后冒烟和观察点；未授权执行
发布时交付这些材料。上线后发现回归则关联原任务继续处理，不丢失已有验收与遗留项。
收尾只报告结果、证据、遗留/UAT、记忆位置和 Git 状态；长期经验确实可复用才写 project.md。
